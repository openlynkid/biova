# ADR-0011: SEO for public pages

- Status: Accepted
- Date: 2026-11-13

## Context

PRD 4.1 lists "SEO metadata" as a public-page feature, and Phase 4 (Growth and
Analytics) is where discovery work belongs. A link-in-bio platform only earns
organic traffic if a creator page can be found: the page needs a canonical URL, a
description a search engine will show, structured data it can turn into a rich
result, and a sitemap that lists it. Without those, a public page is reachable
only by its exact URL.

The public page already emitted a title, a description and a bare `og:title`
from its route `head()`. That is a start, but it leaves three gaps: no canonical
URL, so a page served from a preview host competes with the real one; no
structured data, so products are invisible to search; and no sitemap or robots
file, so crawlers have to guess.

## Decision

### Absolute URLs come from configuration, not the request

Every absolute URL (canonical, `og:url`, sitemap `<loc>`, the sitemap line in
robots.txt) is built from `APP_URL`. The request `Host` header is never used,
because a page served from a preview, tunnel or alternate domain must still point
at the one canonical origin. The origin is read on the server and attached to the
public-page payload, so the client bundle never reads server-only env.

### Metadata and structured data on the page, builders in `@biova/shared`

- The public page `head()` now emits a canonical link, `og:url`, `og:site_name`,
  `og:description` and the Twitter card set, alongside the existing title and
  description.
- Structured data is a schema.org `Person` for the creator, plus an `ItemList` of
  their published products when there are any. It is emitted through the router's
  `script:ld+json` meta slot, which serializes and HTML-escapes it.
- The builders (`buildSitemapXml`, `buildRobotsTxt`, `personJsonLd`,
  `productJsonLd`, `creatorPageJsonLd`, `absoluteUrl`, `escapeXml`) live in
  `@biova/shared/seo` as pure functions, so they are unit-tested without a server
  and reused by both the sitemap route and the page head. Values that reach XML
  are escaped, because a creator-supplied name or bio could otherwise close a tag
  early.

### A sitemap of published pages, and robots that can be read

- `sitemap.xml` lists the home page and every published creator page, with a
  `<lastmod>` from the page row. The query joins creators and filters on
  `status = 'published'`, so a draft or archived page is never advertised.
- `robots.txt` allows crawling, disallows only non-HTML endpoints (`/api/`,
  `/download/`) and advertises the sitemap. Private HTML pages (`/dashboard`,
  `/checkout/...`, `/order/...`) are deliberately *not* disallowed: a crawler
  blocked by robots.txt never reads a `noindex` directive, so a disallowed URL can
  still be indexed from inbound links. Those pages instead carry
  `robots: noindex, nofollow` in their own `head()`, which is the reliable way to
  keep them out of the index.
- The routes are `robots[.]txt.ts` and `sitemap[.]xml.ts`. The bracket escapes
  stop the router treating the dot as a flat-file separator, so the paths are
  exactly `/robots.txt` and `/sitemap.xml`.

## Consequences

- A published page is discoverable: it has a canonical URL, a description, rich
  structured data and a sitemap entry. Unpublishing removes it from the sitemap on
  the next crawl.
- SEO output is testable in isolation, and the escaping rules are covered, so a
  hostile bio cannot break the sitemap XML.
- The site origin is a required production setting. A deployment that forgets
  `APP_URL` falls back to `http://localhost:3000` and publishes wrong canonical
  URLs, so `APP_URL` belongs in the deployment checklist.
- Structured data has no `og:image` yet, because the platform has no image
  pipeline for pages or avatars. A `summary` Twitter card is used until then.
